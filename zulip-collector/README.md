# Zulip Collector

Go-сервис для сбора, фильтрации и хранения сообщений Zulip с последующей интеграцией с данными учебных ведомостей.

## 1. Назначение

Сервис предназначен для сбора сообщений студентов (например БИВ22, БИВ23, БИВ24) из разрешённых публичных каналов Zulip.

Собранные сообщения предполагается связывать с записями студентов в общей PostgreSQL, чтобы в дальнейшем получать сведения из Zulip и учебных ведомостей по одному студенту.

**Текущий статус:** локальный прототип. До предоставления доступа к Zulip API используется синтетический набор данных.

## 2. Архитектура

Основные компоненты:

| Компонент | Назначение |
|---|---|
| `cmd/collector` | Запуск сбора сообщений |
| `cmd/dbcheck` | Проверка подключения к PostgreSQL |
| `cmd/dbsync` | Проверка механизмов синхронизации с БД |
| `internal/collector` | Постраничная обработка, фильтрация и статистика |
| `internal/source` | Источники сообщений; сейчас `FixtureSource` |
| `internal/storage` | Хранение сообщений в памяти |
| `internal/storage/postgres` | Сохранение сообщений и состояния синхронизации |
| `internal/syncmanager` | Модели целей, запусков и контрольных точек синхронизации |
| `migrations` | SQL-структура Zulip |
| `testdata` | Синтетические пользователи, сообщения и принадлежность к группам |

Логика сбора отделена от источника сообщений и способа хранения через Go-интерфейсы `MessageSource` и `MessageStore`.

Это позволяет заменить тестовый источник реализацией Zulip API без переработки основной логики коллектора.

## 3. Реализованная функциональность

- **Постраничное чтение сообщений.** Метод `MessageSource.FetchPage(ctx, cursor)` возвращает `Page` с сообщениями, следующим курсором (`NextCursor`) и признаком завершения (`Done`). Последовательный обход страниц выполняет `Collector.Sync()`.

- **Фильтрация по авторам.** В `Collector.Sync()` используется множество разрешённых идентификаторов `map[int64]bool`. Сообщение включается в выборку при наличии его `AuthorID` в этом множестве. В текущем прототипе состав авторов формируется из синтетических данных.

- **Проверка разрешённых каналов.** В PostgreSQL используется таблица `zulip.channels` с признаком `approved_public`. Ограничение применяется на уровне операций сохранения в `PostgresStore`, предотвращая запись сообщений из неодобренных каналов.

- **Сохранение сообщений и метаданных.** Структура `collector.Message` содержит `ID`, `AuthorID`, `AuthorName`, `ChannelID`, `ChannelName`, `Topic`, `Text`, `URL`, `CreatedAt` и `EditedAt`. Запись в PostgreSQL выполняется через `PostgresStore.SavePage()`.

- **Защита от дубликатов.** Для идентификатора сообщения используется уникальность на уровне PostgreSQL. Повторная обработка реализована через SQL `INSERT ... ON CONFLICT`, что исключает создание второй записи с тем же идентификатором.

- **Обновление существующих сообщений.** При конфликте идентификаторов PostgreSQL выполняет обновление сохранённых полей сообщения. Количество новых и обновлённых записей отражается в результате `SaveResult` и статистике коллектора.

- **Возобновление обработки.** `MessageStore.LoadProgress()` загружает сохранённые `Cursor` и `Done`. Метод `Collector.Sync()` продолжает чтение с сохранённого курсора. Для PostgreSQL состояние хранится в `zulip.sync_state`.

- **Транзакционное сохранение страниц.** `PostgresStore.SavePageWithMetadata()` передаёт метаданные страницы во внутреннюю операцию сохранения. В рамках одной SQL-транзакции обновляются сообщения, курсор, статистика запуска и `last_seen_message_id`. Для защиты состояния используется блокировка `SELECT ... FOR UPDATE`.

- **Метаданные полученных страниц.** Функция `buildPageMetadata()` формирует `PageMetadata`, включающую предыдущий курсор, количество полученных сообщений и максимальный идентификатор сообщения на странице. Метаданные рассчитываются по всем полученным сообщениям, включая исключённые фильтром.

- **Учёт целей синхронизации.** Интерфейс `syncmanager.TargetRepository` и его PostgreSQL-реализация обеспечивают хранение и получение конфигурации целей из `zulip.sync_targets`.

- **Учёт запусков и ошибок.** Интерфейс `syncmanager.RunRepository` описывает операции `StartRun()`, `GetRun()`, `CompleteRun()` и `FailRun()`. Данные запусков хранятся в `zulip.sync_runs`, ошибки — в `zulip.sync_errors`. `StartRun()` создаёт запуск и начальное состояние синхронизации в одной транзакции.

Подготовлены режимы `initial`, `incremental` и `reconcile` через тип `syncmanager.Mode`. Полная реализация стратегий обхода истории ещё не завершена.

## 4. Хранение данных

Используется PostgreSQL со схемой `zulip`.

Основные таблицы:

| Таблица | Назначение |
|---|---|
| `users` | Пользователи Zulip |
| `channels` | Каналы и признак разрешения на сбор |
| `user_groups` | Группы пользователей |
| `group_memberships` | Принадлежность пользователей к группам |
| `messages` | Сохранённые сообщения |
| `sync_state` | Курсоры и состояние обработки |
| `sync_targets` | Параметры целей синхронизации |
| `sync_runs` | История запусков |
| `sync_errors` | Ошибки синхронизации |

Для интеграции с ведомостями используется отдельная схема `integration` общей базы данных. Связи по студентам подготовлены на уровне SQL-структуры; автоматическое сопоставление реальных пользователей пока не реализовано.

## 5. Локальный запуск

Команды выполняются из директории `zulip-collector`.

Проверка тестов:

```bash
go test ./...
go test -race ./...
go vet ./...
```

Запуск коллектора с хранением в памяти:

```bash
go run ./cmd/collector \
  -storage memory \
  -scope fixture-demo-v1
```

Для текущего синтетического набора ожидается:

```text
Страниц: 2
Отобрано: 3
Добавлено: 3
Обновлено: 0
Курсор: 10005
Завершено: true
```

Для работы с PostgreSQL необходимо предварительно создать базу данных, применить SQL-миграции из `migrations` и настроить подключение согласно `internal/config`.

## 6. Тестирование

Реализованы модульные и интеграционные тесты, проверяющие следующие механизмы.

| Проверяемая функциональность | Методы и тесты |
|---|---|
| Фильтрация сообщений | `Collector.Sync()`; `TestCollectorResumeAndReconcile` |
| Постраничная обработка | `MessageSource.FetchPage()`, `Collector.Sync()`; `TestCollectorResumeAndReconcile` |
| Передача метаданных страниц | `buildPageMetadata()`, `SavePageWithMetadata()`; `TestCollectorUsesPageMetadata` |
| Возобновление после остановки | `LoadProgress()`, `SavePage()`; `TestCollectorResumeAndReconcile` |
| Защита от дубликатов | SQL `ON CONFLICT`, `PostgresStore.SavePage()`; проверки в `postgres_test.go` |
| Обновление сообщений | `PostgresStore.SavePage()`; проверки повторной записи в `postgres_test.go` |
| Ограничение по каналам | Проверка `approved_public` при сохранении; тесты `postgres_test.go` |
| Транзакционность PostgreSQL | `BeginTx()`, `Commit()`, `Rollback()`, `SELECT ... FOR UPDATE`; тесты `postgres_test.go` |
| Управление целями синхронизации | `TargetRepository`; тесты `targets_test.go` |
| Управление запусками | `RunRepository`, `StartRun()`, `GetRun()`, `FailRun()`; тесты `runs_test.go` |
| Работа с тестовым источником | `FixtureSource.FetchPage()`; тесты `fixture_test.go` |
| Хранение в памяти | `MemoryStore.LoadProgress()`, `MemoryStore.SavePage()`; тесты `memory_test.go` |

**Подход к тестированию:**

- Unit-тесты проверяют логику коллектора, источника сообщений и хранилища в памяти.
- Интеграционные тесты PostgreSQL проверяют SQL-операции, ограничения целостности и транзакционное поведение.
- Повторные запуски проверяют идемпотентность сохранения и корректность курсоров.
- `go test -race ./...` используется для обнаружения гонок данных в выполняемых тестах.
- `go vet ./...` выполняет дополнительный статический анализ Go-кода.

Тестирование реального Zulip API не проводилось. Полная конкурентная синхронизация нескольких процессов также не считается подтверждённой только прохождением `go test -race`.

## 7. Ограничения и дальнейшая работа

Для завершения интеграции необходимы:

1. Реализация `ZulipSource` для авторизованного доступа к Zulip API.
2. Получение актуальных групп пользователей и разрешённых публичных каналов.
3. Завершение стратегий первоначальной и инкрементальной синхронизации.
4. Проверка выгрузки сообщений в согласованном формате.
5. Сопоставление пользователей Zulip с записями студентов из ведомостей.
6. Документирование процедуры повторного запуска и обновления данных.

**Результат текущего этапа:** реализован и протестирован локальный сборщик с PostgreSQL-хранилищем и подготовленной интеграционной моделью. Реальный сбор сообщений и сквозная выгрузка объединённых данных остаются следующими этапами.
